# 5부. 기술 참조

## 5.1 아키텍처

모노레포(pnpm workspace) 구성이다.

```
apps/api      NestJS 11 + Prisma 6 — REST API, apps/api/src/<module>/ 단위
apps/web      Angular 19 + Ionic 8 — 본사/창고 직원용 PWA
apps/mobile   Capacitor 6 앱(현장 기사용, 이 매뉴얼 범위 밖)
packages/shared  두 프론트엔드가 공유하는 유틸(예: error.util.ts) — 사업자등록번호
                  체크섬은 여기 없다. 실제 위치는 아래 참고
```

**정정**: 사업자등록번호 체크섬 알고리즘은 `packages/shared`가 아니라
`apps/api/src/common/business-registration.ts`에 있다(3.8절). `packages/shared/src/utils/`에는
`error.util.ts`/`index.ts`만 있고 체크섬 관련 파일은 없다(그레핑으로 확인). 창고 실적
엑셀 샘플 생성 스크립트(`scripts/generate-sample-excel.mjs:20`)의 주석은 "packages/shared의
사본"이라고 적어두었지만 실제로는 `apps/api/src/common/business-registration.ts`의
알고리즘을 그대로 복제한 것이다(코드 주석이 부정확 — 알고리즘 자체는 동일하다).

본 매뉴얼이 다루는 API 모듈: `apps/api/src/master-data/`, `apps/api/src/warehouse/`,
`apps/api/src/settlement-fees/`, `apps/api/src/auth/`, `apps/api/src/common/`.
`apps/api/src/settlement/`(레거시 주문·배송 정산)와 `apps/api/src/orders/`,
`apps/api/src/completion/`은 `BRANCH_MANAGER`/`INSTALLER` 역할이 쓰는 별개 기능이며
`SettlementPeriod` 테이블만 창고 모듈과 공유한다(2.4절 E2002 참고).

프론트엔드 라우팅: `apps/web/src/app/app.routes.ts`가 최상위, 각 기능은
`features/<feature>/<feature>.routes.ts`로 지연 로딩(lazy load)되며 `roleGuard`로
보호된다(`apps/web/src/app/core/guards/role.guard.ts`).

## 5.2 데이터 모델 요약

`prisma/schema.prisma` 기준. 이번 마스터데이터·정산 기능으로 신규 추가된 7종 모델과
관련 기존 모델을 정리했다.

| 모델 | 용도 | 주요 필드 | 관계 |
|---|---|---|---|
| `Category` (`:609-623`) | 품목 분류 트리(최대 3단계) | `code`(A / A-01 / A-01-003 형식), `depth`(1~3), `parentId`, `isActive` | 자기참조(`CategoryTree`) |
| `Partner` (`:159-187`) | 거래처(고객사) | `code`, `businessRegistrationNo`(unique, 10자리), `defaultTransportRate`, `isActive` | `storageContracts[]`, `products[]`, `rateHistory[]` |
| `Product` (`:625-647`) | 품목 | `code`(I-00001 형식), `unitPrice`, `costPrice`, `transportRate?`, `palletThreshold?`(%), `maxUnitsPerPallet?` | `Category`, `Partner`, `rateHistory[]` |
| `TransportRateCard` (`:649-662`) | 차량별 운송 단가표 | `vehicleType`, `tonnage?`, `containerSize?`, `specialEquipment?`, `rate` | `WarehouseTransaction.vehicleRate?`, `rateHistory[]` |
| `StorageContract` (`:715-731`) | 거래처별 보관계약 | `contractType`, `palletDailyRate?`, `areaPyeong?`, `areaRate?`, `areaBillingMode`(기본 `FULL_MONTH`), `startDate`, `endDate?`, `isActive` | `Partner` |
| `WarehouseTransaction` (`:733-762`) | 입출고 실적 1건 | `type`(INBOUND/OUTBOUND), `quantity`, `transactionDate`, `source`(PWA/EXCEL), `vehicleRateId?`, **`qtyAfterTransaction`**(Int, NOT NULL — P0-2 누적 잔고, 3.6절) | `Partner`, `Product`, `TransportRateCard?`, `SettlementRecord[]` |
| `SettlementPeriod` (`:490-509`) | 정산 기간 잠금 상태(레거시 정산과 공유) | `branchId`+`periodStart` unique, `periodEnd`, `status`(OPEN/LOCKED), `lockedBy/At`, `unlockedBy/At` | 창고 모듈은 sentinel `branchId='WAREHOUSE'` 사용 |
| `SettlementRecord` (`:764-783`) | 계산된 요금 1건(운송료 건별 또는 보관료 월별) | `transactionId?`(STORAGE는 null), `feeType`(TRANSPORT/STORAGE), `amount`, `periodYearMonth`, `calculationDetail`(Json), **`supersededAt?`**(nullable — P0-3 재마감 버저닝, `null`=최신본, 3.7절) | `WarehouseTransaction?` |
| `ProductTransportRateHistory` (`:673-685`) | 품목 운송요율 이력(P0-1) | `productId`, `rate`, `effectiveFrom`(포함), `effectiveTo?`(배타, null=현재) | `Product`. `(productId, daterange)` EXCLUDE 제약(겹침 금지) |
| `PartnerTransportRateHistory` (`:687-699`) | 거래처 기본요율 이력(P0-1) | 위와 동일 구조, `partnerId` 기준 | `Partner`. 동일 EXCLUDE 제약 |
| `VehicleRateHistory` (`:701-713`) | 차량 단가 이력(P0-1) | 위와 동일 구조, `rateCardId` 기준 | `TransportRateCard`. 동일 EXCLUDE 제약 |
| `SystemSetting` (`:785-791`) | 전역 설정 키-값 저장소 | `key`, `value` | 파렛트 임계 기본값(`pallet_threshold_default`, 미설정 시 코드 기본값 70), 운송료 모드(`vehicle_rate_mode`, 미설정 시 `REPLACE`) |

**관련 enum**: `Role`(`:33-39`, `HQ_ADMIN`/`BRANCH_MANAGER`/`PARTNER_COORDINATOR`/
`INSTALLER`/`WAREHOUSE_STAFF`), `SettlementStatus`(`:41-44`, `OPEN`/`LOCKED`),
`StorageContractType`(`:583-587`, `PALLET_DAILY`/`AREA_MONTHLY`/`AREA_YEARLY`),
`AreaBillingMode`(`:589-592`, `FULL_MONTH`/`DAILY_PRORATED`), `TransactionType`(`:594-597`,
`INBOUND`/`OUTBOUND`), `TransactionSource`(`:599-602`, `PWA`/`EXCEL`), `FeeType`(`:604-607`,
`TRANSPORT`/`STORAGE`).

**요율 이력 3종의 설계 근거**: 폴리모픽 단일 테이블 대신 스코프별로 분리한 3개 테이블을
쓴다(타입 안전성 우선, 스키마 주석 `prisma/schema.prisma:664-671`). `Product`/`Partner`/
`TransportRateCard`의 기존 단일 컬럼(`transportRate`/`defaultTransportRate`/`rate`)은
삭제하지 않고 "현재값 캐시"로 남겨, 이력이 없는 과거 데이터의 폴백 경로와 하위 호환을
유지한다(3.0절).

## 5.5 응답 규약

**성공 응답**: `TransformInterceptor`(`apps/api/src/common/interceptors/
transform.interceptor.ts:43-49`)가 헬스체크를 제외한 모든 응답을
`{ success: true, data: <핸들러 반환값>, timestamp: ISO문자열 }`로 감싼다. 프론트의
axios/HttpClient가 HTTP 바디를 이미 `response.data`에 담으므로, 실제 값에 접근하려면
`response.data.data`까지 내려가야 한다(CLAUDE.md의 "이중 중첩" 규칙과 일치 — 다만
이는 인터셉터 1회 래핑 위에 axios 클라이언트가 한 겹을 더 쌓는 구조이지, 서버가
두 번 감싸는 것은 아니다).

**에러 응답**: 별도의 커스텀 예외 필터가 없다(그레핑으로 확인, 존재하지 않음).
NestJS 기본 필터가 `throw new BadRequestException({code, message})` 형태로 던진
객체를 그대로 직렬화하고 `statusCode`를 추가하므로, 실제 에러 바디는
`{statusCode, code, message}`이며 성공 응답과 달리 `success` 래퍼가 없다. 일부
인증 관련 예외(`auth.service.ts`, `roles.guard.ts`)는 `code` 없이 문자열 메시지만
던진다(예: `error.insufficient_permissions`).

## 5.6 인증과 역할 가드

JWT 페이로드(`apps/api/src/auth/interfaces/jwt-payload.interface.ts:3-12`):
`sub, username, roles: Role[], branchId?, branchCode?, partnerId?, iat?, exp?`.
`partnerId`는 거래처에 연결된 사용자(PARTNER_COORDINATOR)에게만 채워진다. `RolesGuard`
(`apps/api/src/auth/guards/roles.guard.ts`)가 컨트롤러/메서드의 `@Roles()` 메타데이터와
JWT의 `roles`를 대조하며, 미들웨어 체인은 `JwtAuthGuard` → `RolesGuard` 순서다.

## 5.7 로컬 구동 절차

### 5.7.1 인프라 준비

**방법 A — docker compose(권장)**: 저장소 루트 `docker-compose.yml`에 3개 서비스가 정의돼
있다.

| 서비스 | 이미지 | 포트 | 비고 |
|---|---|---|---|
| `postgres` | `postgres:15-alpine` | 5432 | DB `erp_logistics`, 계정 `erp_user`/`erp_password` |
| `redis` | `redis:7-alpine` | 6379 | AOF 영속화(`--appendonly yes`) |
| `adminer` | `adminer:latest` | 8080 | DB GUI(선택) |

```bash
docker compose up -d
```

**방법 B — Homebrew**: `docker-compose.yml`과 동일한 포트/계정으로 맞춰야 `.env`를 그대로
쓸 수 있다.

```bash
brew services start postgresql@15
brew services start redis
createuser erp_user -s                          # 없을 때만
createdb erp_logistics -O erp_user
psql -d erp_logistics -c "ALTER USER erp_user WITH PASSWORD 'erp_password';"
```

포트(5432/6379)나 DB명/계정을 다르게 쓰려면 `.env`의 `DATABASE_URL`/`REDIS_URL`을 그
값에 맞게 바꾼다. (brew 경로는 이 매뉴얼 저장소의 README/CLAUDE.md에 별도로 문서화돼
있지 않아, 표준 Homebrew 설치 절차 기준으로 작성했다 — 실제 로컬 brew 서비스명·버전은
환경마다 다를 수 있으니 `brew services list`로 확인 후 조정한다.)

### 5.7.2 환경변수(`.env`, 저장소 루트)

`.env.example` 기준 필수 키(`apps/api`는 별도 `.env.example`이 없고 루트 `.env`를 그대로 읽는다).

| 키 | 예시값 | 용도 |
|---|---|---|
| `PORT` | `3000` | API 리슨 포트 |
| `DATABASE_URL` | `postgresql://erp_user:erp_password@localhost:5432/erp_logistics` | Prisma 접속 문자열(docker-compose 계정과 일치시켜야 함) |

| `CORS_ORIGINS` | `http://localhost:4300` | 웹 개발 서버 오리진(`.env.example`엔 4200으로 돼 있어 실제 웹 포트 4300과 다름 — 5.7절 하단 참고, 필요 시 직접 4300으로 바꿔야 CORS가 통과함) |

쪽 실제 포트는 `확인 필요`.
