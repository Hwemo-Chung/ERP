# 6부. 운영·제약 사항

[← 목차](./기능-설명서.md)

## 6.1 배포 전 필수 작업

`docs/superpowers/2026-07-25-masterdata-settlement-ledger.md`와
`docs/prd/2026-07-26-erp-benchmark-prd.md`를 근거로 정리했다.

- **미적용 마이그레이션**: PRD §6에 마스터데이터·정산(`masterdata_settlement`),
  sentinel branch 시드, `area_billing_mode` 관련 3건이 배포 환경에 아직 적용되지
  않은 것으로 명시돼 있다. 배포 전 `pnpm db:migrate`(개발) 또는 `prisma migrate
  deploy`(운영)로 적용 여부를 반드시 확인해야 한다.
- **sentinel branch 시드**: 창고 정산 잠금이 쓰는 `WAREHOUSE_SETTLEMENT_BRANCH_ID =
  'WAREHOUSE'`(`apps/api/src/warehouse/constants.ts:4`) 값에 대응하는 시드 데이터가
  준비돼 있는지 확인해야 한다. 이 값이 없으면 `SettlementPeriod` upsert
  (`settlement-fees.service.ts:206-215`)가 참조하는 branch 레코드 정합성이 깨질 수
  있다.
- **E2E_LIVE e2e**: `E2E_LIVE=1` 환경변수로 도는 실환경 e2e 테스트가 실행되지 않은
  상태다(ledger 기준 "e2e 커버리지 0"). 실제 배포 전 이 스위트를 최소 1회 실행해
  월 마감 → 잠금 → 정산서 다운로드까지 이어지는 흐름을 검증하는 것을 권장한다.

## 6.2 알려진 제약

- **웹 유닛테스트 171건 선재 실패**: `ENVIRONMENT_CONFIG` 의존성 주입 문제로 이
  기능들과 무관하게 실패 중인 테스트가 다수 있다(ledger 기준). 새 기능 관련
  회귀인지 판단할 때 이 선재 실패군과 혼동하지 않아야 한다.
- **요율 유효기간 미도입**: 운송 단가/품목 단가에 유효기간(버전 이력)이 없다.
  단가를 수정하면 과거 월을 다시 계산해도(재마감) 새 단가가 적용되므로, **마감
  시점에 따라 같은 달의 금액이 달라질 수 있다**. PRD의 요율 버저닝(P0-1,
  `ProductTransportRateHistory` 등)이 도입되기 전까지는 요율 변경 시점과 마감
  시점을 운영적으로 맞춰 관리해야 한다.
- **재마감 시 이전 계산 소멸**: `closeMonth`는 해당 월의 `SettlementRecord`를 전부
  삭제 후 재생성한다(`settlement-fees.service.ts:200-201`,
  `deleteMany`→`createMany`). 이전 마감 결과가 별도로 보존되지 않으므로, 재마감
  전후 금액 차이를 추적하려면 마감 전에 정산서를 별도로 다운로드해 보관해야 한다.
- **보관료 계산 경로의 예외 처리 비대칭**(3.5절 상세): 운송료 계산은
  `computeMonth` 안에서 `try/catch`로 감싸져 `E4108`이 오류 목록에 정상 수집되지만,
  보관료 계산(`calcStorageFeePalletDaily`/`calcStorageFeeArea`)은 감싸져 있지 않다.
  품목의 `maxUnitsPerPallet`이 0 이하로 잘못 등록되면 미리보기가 오류 배지 없이
  알 수 없는 오류(500 추정)로 실패할 수 있다. 이 경우 해당 월 거래에 걸린 품목들의
  파렛트당 최대적재수 설정을 먼저 점검해야 한다.
- **누적 재고 재계산 방식**: 전월 이월재고(`openingStock`,
  `settlement-fees.service.ts:172-184`)를 매번 해당 거래처의 **전체 이력**을 다시
  훑어 계산한다(누적 잔고 컬럼 없음). 거래 이력이 많은 거래처는 월 마감 소요
  시간이 늘어날 수 있다(PRD P0-2, `qtyAfterTransaction` 컬럼 도입 전까지는
  구조적 한계).
- **테스트 통과 건수 문서 간 불일치**: ledger는 API 테스트 최종 362/362, PRD는
  385/385로 서로 다른 수치를 적고 있다. PRD가 이후 브랜치(정산 옵션화 등)에서
  늘어난 수치를 반영한 것으로 추정되나 `확인 필요` — 배포 전 실제
  `pnpm --filter erp-logistics-api run test` 실행 결과로 재확인해야 한다.
- **거래처/수정 화면의 상세 조회 API 부재**: `GET /master-data/partners/:id`,
  `GET /master-data/products/:id`가 없어 프론트가 목록 화면에서 넘긴 라우터 상태에만
  의존한다(4.1절). URL 직접 진입이나 새로고침 시 데이터가 사라지는 것은 버그가
  아니라 이 구조적 한계 때문이다.

## 6.3 향후 계획 (미구현 — 참고용 링크만)

아래 항목은 `docs/prd/2026-07-26-erp-benchmark-prd.md`에 계획으로만 존재하며, 현재
코드베이스에는 구현돼 있지 않다. 이 매뉴얼의 다른 파트에서 "구현됨"으로 서술한
내용과 절대 혼동하지 않아야 한다.

- P0-1: 요율 유효기간 버저닝(`ProductTransportRateHistory` 등 3개 테이블)
- P0-2: `qtyAfterTransaction` 누적 잔고 컬럼(현재는 전체 이력 스캔 방식)
- P0-3: 재마감 시 이전 계산 보존(`supersededAt`) — 현재는 삭제 후 재생성
- P1-1: `SettlementInvoice` 청구서 문서화(번호/상태/부가세/PDF)
- P1-2: 바코드 스캔 입력
- P1-3: 조정 트랜잭션 타입(`ADJUSTMENT_IN`/`ADJUSTMENT_OUT`)
- P1-4: 재고 임계 알림
- P2군: 재고 실사, 기사 위치 추적, 로케이션 관리, 공유 타입 정리, ASN

자세한 내용은 `docs/prd/2026-07-26-erp-benchmark-prd.md` 원문을 참고한다.

### 반영된 개선 (PRD P0)

- **P0-1 요율 유효기간**: 요율에 적용 시작일이 생겼다. 정산은 **거래일 기준** 요율로 계산되므로, 마감을 언제 실행해도 금액이 동일하다. 요율 변경 화면에 적용 시작일 입력과 이력 목록이 추가됐다. 이력이 없는 과거 거래는 현재값(캐시 컬럼)으로 폴백한다.
- **P0-2 누적 잔고**: 거래 행마다 누적 잔고를 저장해 재고 조회가 인덱스 1행 조회로 바뀌었다. 과거 일자로 실적을 늦게 입력하면 이후 행이 자동 재계산되고 감사 로그가 남는다. 동일 거래처·품목 동시 입력은 advisory lock으로 직렬화된다.
- **P0-3 재마감 버저닝**: 재마감 시 이전 계산을 삭제하지 않고 `supersededAt`으로 마킹해 보존한다. 조회는 최신본만 노출된다. 재마감 시 감사 로그에 이전 총액 → 신규 총액이 기록된다.

### 여전히 남은 제약

- 위 마이그레이션 6건이 실 DB에 적용되지 않은 상태다. 적용·검증은 배포 게이트에서 수행해야 한다.
- advisory lock·EXCLUDE 제약·백필 결과는 실 Postgres에서 1회 실증이 필요하다(샌드박스에 DB 없음).
- 웹 유닛 테스트 171건 선재 실패(`ENVIRONMENT_CONFIG` DI 문제)는 이 작업들과 무관하며 미해결이다.
