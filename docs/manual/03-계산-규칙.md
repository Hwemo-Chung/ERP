# 3부. 계산 규칙

[← 목차](./기능-설명서.md)

이 파트는 돈과 직결되는 부분이라 코드와 1:1로 대조했다. 예시 숫자는 전부
`*.spec.ts` 테스트 케이스에서 검증된 값을 그대로 가져왔고, 필자가 직접 재계산해
일치를 확인했다.

## 3.0 요율은 거래일 기준으로 조회한다 (P0-1, `apps/api/src/settlement-fees/rate-resolution.ts`)

품목 운송요율/거래처 기본 운송요율/차량 단가 3종 모두 값 하나가 아니라 **이력**을 갖는다
(`ProductTransportRateHistory`/`PartnerTransportRateHistory`/`VehicleRateHistory`,
`prisma/schema.prisma:673-713`). 각 이력 행은 `effectiveFrom`(포함, `@db.Date`)과
`effectiveTo`(배타, `null`이면 현재까지 유효)를 갖는다. 월 마감/미리보기는 각 거래(출고)의
`transactionDate`가 `effectiveFrom <= 거래일 < effectiveTo`(또는 `effectiveTo IS NULL`)를
만족하는 행을 찾아 그 요율을 적용한다(`resolveRateAt`, `rate-resolution.ts:19-25`). **마감을
실행하는 시각의 "현재 요율"이 아니라 거래가 일어난 그 날짜의 요율**을 쓰므로, 같은 달을
언제 마감하든 금액이 동일하다(`settlement-fees.service.ts:56-59` 주석).

이력이 아예 없는 스코프(백필 이전 데이터 등)는 `Product.transportRate` /
`Partner.defaultTransportRate` / `TransportRateCard.rate`의 "현재값 캐시" 컬럼으로 폴백한다
(`settlement-fees.service.ts:94-97,99-101,103-105`). 이력도 캐시도 없으면 3.1절의 `E4108`
경로로 떨어진다.

**기간 겹침은 DB가 막는다**: `product_transport_rate_histories` 등 3개 테이블 모두
`EXCLUDE USING gist (scope_id WITH =, daterange(effective_from, effective_to) WITH &&)`
제약이 걸려 있다(`prisma/migrations/20260726120000_transport_rate_history/migration.sql:78-99`,
`btree_gist` 확장 필요). 같은 거래처/품목/차량에 대해 기간이 겹치는 이력 행을 INSERT하면
Postgres가 거부한다(6부 6.1절에 실제 거부 로그 실증).

**요율 변경 화면**: 거래처/품목/차량 단가표 수정 화면에는 "적용 시작일" 입력이 있다
(`partner-form.page.ts:43`, `product-form.page.ts:59`, `rate-cards.page.ts:45,87`, 4부 참고).
비워두면 서버가 오늘 날짜(UTC 자정 정규화)를 기본값으로 쓴다(`rates.service.ts:13-16`
`todayDateOnly()`). 저장하면 서버가 같은 트랜잭션 안에서 열린 이력 행(`effectiveTo: null`)의
`effectiveTo`를 새 적용 시작일로 닫고, 새 행을 연다(`partners.service.ts:152-165`,
`products.service.ts:84-97`, `rates.service.ts:68-80`). 각 화면에는 이력 목록도 함께 표시된다
(`{h.effectiveFrom} ~ {h.effectiveTo || '현재'} : {h.rate}` 형식). 이력 조회 API 3개는 모두
HQ_ADMIN 전용이다(5.3절).

**`E4113`**: 새 적용 시작일이 현재 열린 이력 행의 시작일보다 **이후**여야 한다
(`assertRateEffectiveFromAdvances`, `apps/api/src/common/rate-effective-from.util.ts:12-19`).
같거나 이전 날짜를 입력하면 `effectiveTo <= effectiveFrom`인 잘못된 기간이 만들어지거나
DB EXCLUDE 제약과 충돌하므로, 이를 `{code, message}` 형태의 400으로 먼저 막는다(그러지
않으면 raw 500이 나갔을 것이라고 코드 주석에 명시돼 있다).

**실측 예시(DEMO-A 대한물류, 로컬 데모 데이터로 직접 확인)**: 기본 운송요율 이력이
`2026-07-01~07-16(배타) = 3,000원`, `2026-07-16~(현재) = 4,000원`으로 등록돼 있다. 이 상태에서

- 2026-07-10 출고 실적의 계산근거(`GET /settlement-fees/breakdown/:id`) → `amount: "3000"`,
  `rateSource: PARTNER_DEFAULT`, `formula: "건당 고정 요율 3000 (PARTNER_DEFAULT)"`.
- 2026-07-17 출고 실적의 계산근거 → `amount: "4000"`, 나머지 동일 형식.

두 건 모두 2026-07 마감이 **이미 완료된 상태**(마감 실행 시각은 두 건 다 동일)에서
조회한 값이며, 마감 시점이 아니라 거래일에 따라 요율이 갈린 것을 확인했다.

## 3.1 운송료 (`apps/api/src/settlement-fees/transport-fee.ts`)

**우선순위**: 차량 단가(`VEHICLE`) > 품목 단가(`PRODUCT`) > 거래처 기본 단가
(`PARTNER_DEFAULT`) (`transport-fee.ts:22-28`). 셋 다 없으면
`E4108: no transport rate configured`(`transport-fee.ts:29`)를 던진다.

**REPLACE 모드**(전역 설정 기본값): 우선순위가 가장 높은 요율을 그대로 적용한다.
계산식 문자열: `건당 고정 요율 {rate} ({rateSource})`(`transport-fee.ts:50-58`).

| 예시 | 차량단가 | 품목단가 | 거래처기본단가 | 결과 | 요율출처 |
|---|---|---|---|---|---|
| 1 | 120,000 | 5,000 | 3,000 | 120,000 | VEHICLE |
| 2 | (없음) | 5,000 | 3,000 | 5,000 | PRODUCT |
| 3 | (없음) | (없음) | 3,000 | 3,000 | PARTNER_DEFAULT |

**ADD 모드**: 차량 단가가 있을 때만 REPLACE와 달라진다 — `차량단가 + (품목단가 ??
거래처기본단가 ?? 0)`(`transport-fee.ts:34-48`). 차량 단가가 없으면 ADD도 REPLACE와
동일하게 품목→거래처 순으로 폴백한다(`transport-fee.spec.ts` 확인).

| 예시 | 차량단가 | 품목단가 | 거래처기본단가 | 결과 | 계산식 |
|---|---|---|---|---|---|
| 4 | 120,000 | 5,000 | — | 125,000 | 차량 단가 120000 + 건당 요율 5000 = 125000 |
| 5 | 120,000 | (없음) | 3,000 | 123,000 | 차량 단가 120000 + 건당 요율 3000 = 123000 |
| 6 | 120,000 | (없음) | (없음) | 120,000 | 차량 단가 120000 + 건당 요율 0 = 120000 |

`E4108` 발생 조건은 REPLACE/ADD 공통이다(셋 다 없을 때).

## 3.2 보관료 — PALLET_DAILY

### 파렛트 환산 (`apps/api/src/settlement-fees/pallet.ts:8-21`)

```
fullPallets = floor(수량 / 파렛트당최대수량)
remainder   = 수량 % 파렛트당최대수량
remainderRatio = remainder / 파렛트당최대수량
extra = remainderRatio >= 임계% / 100 ? 1 : 0
파렛트수 = fullPallets + extra
serviced = 파렛트수 === 0 && 수량 > 0   // 서비스 처리(무과금)
```

`파렛트당최대수량 <= 0`이면 `E4107: maxUnitsPerPallet must be positive`
(`pallet.ts:9`)를 던진다. 임계 %는 품목별 오버라이드(`Product.palletThreshold`)가
있으면 그 값을, 없으면 전역 설정값을 쓴다(`storage-fee.ts:72`).

**임계 70%, 파렛트당최대수량 100 기준 예시** (`pallet.spec.ts`):

| 수량 | fullPallets | 잔여비율 | extra | 파렛트수 | 비고 |
|---|---|---|---|---|---|
| 69 | 0 | 69% | 0 | **0** | 서비스 처리(무과금) |
| 70 | 0 | 70% | 1 | **1** | 임계값 경계 포함(`>=`) |
| 100 | 1 | 0% | 0 | **1** | 만재 |
| 150 | 1 | 50% | 0 | **1** | 만재 1 + 잔여 50% < 70% |
| 170 | 1 | 70% | 1 | **2** | 만재 1 + 잔여 70% |
| 370 | 3 | 70% | 1 | **4** | 만재 3 + 잔여 70% |

품목별 임계 오버라이드 예시: 임계 50%, 파렛트당최대수량 100일 때 수량 50 →
잔여비율 50% ≥ 50% → 1파렛트(전역 70% 기준이었다면 0파렛트/서비스 처리였을 것).

### 일별 재고 산출 (`storage-fee.ts:6-31`)

**이월재고**(`openingStock`, `settlement-fees.service.ts:228-236`)에서 시작해, 대상 월의
1일부터 말일까지 매일 입고(+)/출고(−) 델타를 누적한다(running total, UTC 날짜 기준으로
거래를 매칭, 대상 월 밖 거래는 무시). **P0-2 이후**: 이월재고는 더 이상 거래처의 전체
이력을 훑지 않는다 — 거래 행마다 저장되는 누적 잔고(`qtyAfterTransaction`, 아래 3.6절)
덕분에, 품목별로 "대상월 이전 가장 최근 1행"만 `DISTINCT ON` 조회로 읽으면 된다
(`$queryRaw`, `settlement-fees.service.ts:229-234`). 파라미터는 태그드 템플릿 바인딩이라
SQL 인젝션 걱정 없이 원시 쿼리를 쓴다.

### 파렛트일 합산과 금액 (`storage-fee.ts:71-85`)

- 일별 재고가 **양수인 날만** 그 날의 파렛트 수를 더해 총 파렛트일수를 구한다.
- 재고가 **음수인 날**은 과금하지 않고 `negativeStockProducts`에 기록한다(입고 누락
  의심 경고, breakdown 화면에 표시).
- `파렛트당최대수량`이 없는 품목은 `skippedProducts`에 기록하고 계산에서 제외한다.
- **금액 = 파렛트 일단가 × 총 파렛트일수**.

**예시**: 2일간 매일 재고 150(각 1파렛트), 파렛트 일단가 1,000 →
총 파렛트일수 2 → 금액 = 1,000 × 2 = **2,000**.

## 3.3 보관료 — AREA_MONTHLY / AREA_YEARLY (`storage-fee.ts:113-149`)

```
gross = 면적(평) × 평당단가
월정액 = (계약유형 === AREA_YEARLY) ? gross / 12 : gross   // 년임대는 12분할
```

**청구 방식(`areaBillingMode`, 기본값 `FULL_MONTH`)**:

- `FULL_MONTH`(월할 고정): 금액 = 월정액 그대로.
- `DAILY_PRORATED`(일할): 금액 = 월정액 × (대상월과 계약기간이 겹치는 일수) /
  (대상월 전체 일수), 소수점은 반올림(`toFixed(0)`). 겹치는 일수는 계약
  `[startDate, endDate ?? 무한대]`와 대상 월의 교집합 일수이며 `endDate`는 포함이다
  (`coveredDaysInMonth`, `storage-fee.ts:102-111`).

**예시 — AREA_MONTHLY, 100평 × 10,000원, FULL_MONTH**: 금액 = 100 × 10,000 =
**1,000,000**.

**예시 — AREA_YEARLY, 120평 × 12,000원, FULL_MONTH**: 월정액 = 120 × 12,000 / 12 =
**120,000**.

**예시 — DAILY_PRORATED (2026년 7월, 31일)**

| 케이스 | 계약 기간 | 겹치는 일수 | 계산 | 금액 |
|---|---|---|---|---|
| 월 중간 시작, 무종료 | 7/16 ~ | 16일 | 1,000,000 × 16 / 31 | 516,129 |
| 이전 달부터 계약, 월 중간 종료 | 6/1 ~ 7/10 | 10일 | 1,000,000 × 10 / 31 | 322,581 |
| 계약이 대상월 전체를 덮음 | 6/1 ~ 8/31 | 31일 | 1,000,000 × 31 / 31 | 1,000,000 (FULL_MONTH와 동일) |
| 계약이 대상월과 겹치지 않음 | 8/1 ~ | 0일 | 1,000,000 × 0 / 31 | 0 |
| AREA_YEARLY + 일할 | 7/1 ~ 7/15(월정액 120,000) | 15일 | 120,000 × 15 / 31 | 58,065 |

마지막 예시가 보여주듯 **년임대는 12분할을 먼저 적용한 뒤** 그 월정액에 일할
비례를 적용한다(두 단계가 순차 적용, 곱셈 순서가 뒤바뀌지 않음).

**실측 예시(DEMO-B 한국유통, 로컬 데모 데이터로 직접 확인)**: `AREA_MONTHLY`, 120평 ×
9,000원/평, `areaBillingMode: DAILY_PRORATED`, 계약 시작일 2026-07-10(종료일 없음).

- 월정액(FULL_MONTH였다면의 금액) = 120 × 9,000 = **1,080,000원**.
- 대상월 2026-07(31일)과 계약기간 `[7/10, ∞)`의 교집합 일수 = 7/10~7/31 = **22일**.
- 최종 금액 = 1,080,000 × 22 / 31 = 766,451.612... → 반올림 = **766,452원**.

`GET /settlement-fees/statement?partnerId=<DEMO-B>&yearMonth=2026-07`를 직접 호출해
`storage.total`이 정확히 `"766452"`로 나오는 것을 확인했다(계산 코드가 아니라 마감 완료된
실제 응답 값 기준).

반올림은 `Prisma.Decimal.toFixed(0)`이 수행하며(`storage-fee.ts:129-131`, 기본 반올림
모드는 사사오입/HALF_UP), 이 값은 애초에 딱 떨어지는 `.5`가 아니라서(766451.612903...)
반올림 방식에 따른 모호함 자체가 없다.

날짜 계산은 로컬 타임존이 아니라 UTC 기준 자정으로 맞춘다(`daysInMonthUTC`,
`storage-fee.ts:97-99`) — `@db.Date` 컬럼과 비교가 항상 날짜 단위로 맞아떨어지게 하려는
의도라고 코드 주석(`:94-96`)에 명시돼 있다.

## 3.4 정산 기간 경계 규칙

`periodEnd`는 **배타적(exclusive)** 경계로 저장한다 — 예를 들어 7월을 마감하면
`periodEnd`는 "8월 1일 0시(UTC)"가 저장되며 "7월 31일 23:59:59"가 아니다
(`settlement-fees.service.ts:22-35`의 `monthRange()`). 이를 참조하는 두 곳이 항상
짝을 맞춰야 하는 "결합 불변식(COUPLED INVARIANT)"으로 코드에 명시돼 있다.

- 마감월 계산 조회: `transactionDate: { gte: start, lt: end }`
  (`settlement-fees.service.ts:47`)
- 실적 입력 잠금 게이트: `periodEnd: { gt: txDate }`(`transactions.service.ts:39`,
  엄격히 초과 — 배타 경계이므로 `gt`가 정확)

**왜 배타 경계로 했는가(한 줄 요약)**: 월말을 "23:59:59 포함"으로 표현하면 타임존/
날짜형 정밀도 차이로 경계에서 off-by-one이 생기기 쉬운데, "다음 달 1일 0시 미만"
(exclusive)으로 통일하면 `@db.Date`가 날짜만 저장하든 타임스탬프까지 저장하든
비교가 항상 정확하다(코드 주석 `settlement-fees.service.ts:24-32`).

## 3.5 알려진 계산상 결함(코드 대조로 확인)

`computeMonth`(`settlement-fees.service.ts:39-206`) 내부에서 운송료 계산
(`calcTransportFee` 호출, `settlement-fees.service.ts:90-120`)은 `try/catch`로 감싸여
있어(`:90`,`:118-120`) `E4108`이 발생해도 오류 목록에 깔끔하게 수집된다. 반면 보관료 계산
(`calcStorageFeePalletDaily` 호출부 `:129-156`, `calcStorageFeeArea` 호출부 `:158-167`)은
**try/catch로 감싸여 있지 않다**. 따라서 품목의 `maxUnitsPerPallet`이 0 이하로 잘못 등록돼
`E4107`이 발생하면, 미리보기/마감 API가 오류 목록에 담아 보여주는 대신 처리되지
않은 예외로 500 응답을 낼 가능성이 높다. 실무자 입장에서는 미리보기 화면이 정상
오류 배지 대신 알 수 없는 오류로 실패하면 파렛트당최대수량이 0 이하로 등록된
품목이 없는지 마스터데이터를 먼저 점검해야 한다(6부 운영·제약 사항 참고).

## 3.6 누적 잔고 (P0-2, `apps/api/src/warehouse/transactions.service.ts`)

**목적**: 재고 조회를 "거래처의 전체 이력 스캔"에서 "인덱스 1행 조회"로 바꿔, 거래 이력이
많은 거래처의 월 마감 속도가 이력 길이에 비례해 느려지지 않게 한다.

**규칙**: `WarehouseTransaction.qtyAfterTransaction`(정수, NOT NULL,
`prisma/schema.prisma:749`)에 그 거래 시점까지의 (거래처, 품목) 단위 누적 잔고를 저장한다.
정렬 키는 항상 `(transactionDate, id)` 오름차순이다(같은 날짜는 `id`로 동점 처리).

- **신규 등록 시**: 직전 행(같은 정렬 키 기준 바로 앞) 1건만 조회해 `+수량`(INBOUND)/
  `-수량`(OUTBOUND)을 더한다(`transactions.service.ts:70-79`).
- **동시성 보호**: 같은 (거래처, 품목) 조합에 동시에 두 건이 들어오면 READ COMMITTED
  하에서 둘 다 같은 "직전 잔고"를 읽어 잔고 사슬이 깨질 수 있다. 이를 막기 위해
  트랜잭션 시작 직후 첫 문장으로 Postgres advisory lock을 건다
  (`pg_advisory_xact_lock(hashtext(partnerId||':'||productId))`,
  `transactions.service.ts:68`) — 두 번째 호출은 첫 번째가 커밋될 때까지 블로킹된다.
- **소급(과거 일자) 입력**: 새로 넣은 행보다 정렬 키가 뒤인 기존 행 전부를 다시 조회해
  누적 잔고를 처음부터 다시 계산하고 업데이트한다(`transactions.service.ts:99-117`).
  영향받은 행이 1건 이상이면 감사 로그(`AuditLog`, `action: 'RETROACTIVE_QTY_RECALC'`)에
  영향 행 수와 삽입된 거래일을 기록한다(`:118-127`, 행별이 아니라 재계산 1건당 로그
  1건).
- **잔고 조회**: 월 마감의 이월재고(3.2절 `openingStock`)는 `DISTINCT ON (product_id) ...
  ORDER BY product_id, transaction_date DESC, id DESC` 형태로 품목별 최신 1행만 읽는다
  (`settlement-fees.service.ts:229-234`).

**검증 스크립트**: `node scripts/verify-qty-after-transaction.mjs`(실행에는 `DATABASE_URL`이
필요 — `apps/api/.env`를 로드해서 실행)는 모든 `warehouse_transactions` 행을 (거래처, 품목)
별로 (거래일, id) 순 재계산해 저장된 `qty_after_transaction`과 대조한다. 실제 로컬 환경에서
실행한 결과:

```
Checked 24 warehouse_transactions rows.
OK: every row's qty_after_transaction matches its recomputed running balance.
```

## 3.7 재마감 버저닝 (P0-3, `apps/api/src/settlement-fees/settlement-fees.service.ts:243-317`)

**목적**: 이미 마감된 월을 다시 마감할 때(실적 정정 후 재계산 등) 이전 계산 결과를
지우지 않고 남겨서, 청구 분쟁이 생겼을 때 "그때 왜 그 금액이었는지"를 추적할 수 있게 한다.

**규칙**: `SettlementRecord.supersededAt`(nullable, `prisma/schema.prisma:773`)이
`null`이면 최신본(살아있는 레코드), 값이 있으면 대체된 이전 레코드다. 재마감 시 서버는:

1. 재마감 **이전**의 총액을 먼저 읽는다(`supersededAt: null`인 행의 `amount` 합,
   `settlement-fees.service.ts:258-265`) — 마킹 이후에 읽으면 안 되므로 순서가 고정돼 있다.
2. 그 달의 살아있는 레코드 전체를 `supersededAt: new Date()`로 마킹한다(`deleteMany`가
   아니라 `updateMany`, `:269-272`).
3. 새로 계산한 레코드를 `createMany`로 추가한다(`:273`).
4. 대체된 행이 1건 이상이면 감사 로그(`action: 'SETTLEMENT_RECLOSE'`)에 연월, 대체 건수,
   이전 총액, 신규 총액을 기록한다(`:287-309`).

**이중 계상 방지 확인**: 조회 경로 3곳 모두 `supersededAt: null` 필터를 건다 —
`getBreakdown`(`:320-321`), `getStatement`(`:334-336`), 재마감 시 "이전 총액" 집계
(`:258-261`). 세 곳 모두 확인했으며 필터가 빠진 집계 지점은 없다 — 재마감을 여러 번
반복해도 정산서 금액이 이중으로 잡히지 않는다.

## 3.8 사업자등록번호 체크섬 (`apps/api/src/common/business-registration.ts`)

거래처 등록/수정 시 `E4101`을 판정하는 알고리즘이다(2.1절·4.1절에서 이 절을 참고한다).

```
WEIGHTS = [1, 3, 7, 1, 3, 7, 1, 3, 5]
sum = Σ(앞 9자리[i] × WEIGHTS[i])  (i = 0..8)
sum += floor(9번째 자리(0-based 8번 인덱스) × 5 / 10)
검증 = (10 - (sum % 10)) % 10 === 10번째 자리(체크 digit)
```

하이픈은 검증 전에 제거한다(`normalizeBrn`, `:3-5`). 10자리 숫자가 아니면 즉시 `false`
(`:9`). `docs/samples/partners-sample.xlsx`의 정상 8건은 이 알고리즘을 통과하도록
생성돼 있고, `KM003` 행은 마지막 자리를 고의로 틀려 `E4101`을 재현한다(2.2절).
`scripts/generate-sample-excel.mjs:20-27`에 동일 알고리즘의 JS 사본이 있다(TS를 직접
import할 수 없는 plain Node 스크립트라 값만 복제, 로직 변경 시 두 곳을 함께 고쳐야 한다).
